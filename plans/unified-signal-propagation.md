# Unified Signal Metadata and Automatic Propagation

## Status Quo
Currently, signal metadata (like "struct-ness" or "interface-ness") is stored in separate maps within the `Module` structure (`structSignals`, `interfaceSignals`). Propagation of this metadata across procedural blocks, muxes, and combinational shims is handled manually by calling specific helpers (like `propagateStruct`) during the lowering process. This is error-prone, specific to one type of aggregation, and leads to code duplication across `procedural.inc`, `modules.inc`, and `expressions.inc`.

## Objective
Implement a unified, type-agnostic signal registry and an automatic propagation engine that ensures metadata (width, aggregate kind, type names) is preserved across all graph nodes without requiring manual intervention in the extraction logic.

## Suggested Plan of Attack

### 1. Unified Signal Registry
Consolidate separate maps into a single `SignalRegistry` within the `Module` struct.

```cpp
struct SignalMetadata {
    std::string name;
    std::string width;
    std::string aggregateKind; // "scalar", "struct", "interface", "array"
    std::string typeName;      // e.g., "my_struct_t"
    SourceInfo source;
    // Store type-specific details (fields for structs, modports for interfaces)
    // using a variant or a generic property map.
};

// Inside struct Module:
std::map<std::string, SignalMetadata> signalRegistry;
```

### 2. Immediate Automatic Discovery
During the initial declaration pass (ports, nets, variables), populate the `SignalRegistry`. Any time a new signal name is generated (e.g., `_next`, `_if_0`), it should immediately be entered into the registry with a "pending" type.

### 3. Automatic Propagation Engine (Post-Processing)
Instead of manual propagation during node creation, implement a post-processing pass that runs after the module's graph is fully built but before `buildEdges`.

#### Discovery Rules
The engine will traverse the nodes and apply "transfer functions":
- **Transparent Nodes** (Mux, If, Buffer/Alias, Loop): These nodes have a primary output signal that "inherits" the type of its data inputs.
- **Transformative Nodes** (ALU, Inverter, Logic): These nodes typically output a packed vector or scalar.
- **Structural Nodes** (Struct Breakout/Composition, Bus Select/Tap): These nodes explicitly change the aggregate type (e.g., struct -> scalar field).

#### The Propagation Pass
1.  **Forward Pass**: For each node, if the input signals have a known `aggregateKind`, propagate it to the output signal in the `SignalRegistry`.
2.  **Convergence**: Repeat until no more type information can be inferred. This handles chains of muxes and intermediate aliases.

### 4. Agnostic Edge Tagging
Refactor `buildEdges` to be completely data-driven:
- It looks up the `signal` name in the `SignalRegistry`.
- It automatically sets `e.aggregateKind`, `e.width`, and `e.isStacked` based on the registry entry.
- No more manual `if (mod.structSignals.count(signal))` checks.

### 5. Benefits
- **Extensibility**: Adding a new aggregate type (e.g., `union` or `enum` styling) only requires updating the registry model, not the entire extraction logic.
- **Robustness**: Intermediate signals generated by complex expressions will automatically inherit the correct styling because they are connected via edges to typed sources.
- **Cleaner Code**: Removes the need for `propagateStruct`, `propagateInterface`, etc., from the core procedural lowering logic.

## Implementation Steps
1.  **Refactor `Module`**: Merge existing signal maps into `signalRegistry`.
2.  **Update Discovery**: Update `collectStructSignal`, `processModuleInterfaces`, and `getDeclaredSignalWidth` to write to the unified registry.
3.  **Implement Engine**: Create a new file `src/parser/backend_cpp/src/extractor_parts/type_engine.inc` to hold the propagation logic.
4.  **Hook into `processModule`**: Call the type engine after processes and assignments are parsed but before edge construction.
5.  **Simplify `buildEdges`**: Remove all type-specific logic and replace with a registry lookup.
